9. 小心，Claude Code会擅自泄露你的邮箱！请抓紧时间更新

11-08 21:11 原文链接

新智元报道

用户每月掏几十甚至 200 美元订阅 Claude Code，把本地终端交给它干活，它却在后台把你的真实登录邮箱、姓名乃至公司内部代码库地址，塞进 User-Agent 请求头里发给了外部网站！

Anthropic 工程师图省事，偷偷把登录邮箱硬编码进每次对话的系统提示词，而 Claude，一遇到要求登记联系方式的网站，就顺手从提示词里取出真邮箱发了出去。

图省事，出卖了用户隐私

2026 年 11 月 5 日，Hacker News 上一条控诉 Claude Code 外发用户邮箱的帖子迅速冲上了热门。

发帖人每天收到几十封直呼真名的诈骗邮件，发信域名他一个也没访问过。

顺着请求记录一查，Claude Code 联网抓数据时，竟然往 HTTP 请求的 User-Agent 头里拼上了会话名和他的真邮箱。

评论区很快有人贴出更吓人的服务器日志，Claude Code 派出的子智能体请求外部文档时，直接把使用者真名、所在团队名称和公司内部 GitHub 仓库路径全写进了请求头。

起初不少人猜是模型中了外部网页的提示词注入。

直到 11 月 6 日凌晨，Claude Code 工程师 Lydia Hallie 出面道歉，才把起因交代清楚。

早先有用户反映 Claude 生成 author 注释标签时会胡编人名，原因在于模型拿不到账号信息。

工程团队图省事，直接从本地配置读取登录邮箱，塞进了给模型的系统上下文。

工程团队没算到这步操作遇上大模型死磕任务的习惯会出什么乱子。

用户让 Claude 调取美国证监会 SEC 财报、维基百科、crates.io 或游戏 EVE Online 接口时，这些平台为防爬虫，都要求脚本在请求头里留下联系邮箱，否则直接返回 403 拒绝访问。

调用美国证监会 SEC API 时，Claude 被「提示注入攻击」了

系统自带的 curl 默认不带这类信息，受过强化学习训练的大模型为了越过报错跑通任务，看见上下文里存着用户邮箱，便自作主张拼进命令发了出去。

评论区有位开发者用爬虫抓接口被封 IP，专门花钱买来轮换住宅代理隐匿身份，Claude 给爬虫写请求头时却直接填上他的真邮箱，事后还解释说这样做方便对方网站遇到问题时直接写信联系，免得再次封禁 IP。（Claude：咱都是为你好）

反编译，查出了真相

这桩事到 11 月初才彻底闹大，翻看 GitHub 历史记录就会发现，知情的用户已经折腾了大半年。

早从 2026 年 4 月起，社区就提交过 50702 号、53231 号等至少 4 个工单，指出账号邮箱被强行塞进上下文且无法关闭，结果全被官方机器人以不活跃或重复为由自动关掉。

7 月中旬又有用户因 curl 泄露邮箱提交 78431 号工单，8 月上过一次 Hacker News，到 9 月照样被机器人关闭。

常规反馈没人理，开发者 skflowne 便在 7 月 25 日反编译了 Claude Code v2.1.220 安装包，交出一份证据详尽的 81138 号报告。

代码显示，客户端每次启动都会从本地配置读取登录邮箱，拼成一句英文提示词。

翻遍整个代码包，这个字段除了在两处遥测事件里统计布尔值，没有任何业务功能读取它，官方文档和设置页里也只字未提。

反编译还查出一个讽刺的细节。Claude Code 有个名为 IS_DEMO 的环境变量，官方文档专门推荐主播在直播或录屏时将它设为 1，用来隐藏状态栏里的邮箱和组织名。

然而程序包里全部 7 处 IS_DEMO 判断只拦截了屏幕表层的文字显示，根本没碰模型上下文。

主播以为打开演示模式就能安心直播，邮箱却原封不动留在模型上下文里。提交报告的开发者就亲身遇上两次事故。

一次是模型解释其他错误时，冷不丁在终端打出自己从系统提示词看到了他的邮箱。

另一次是模型连续 10 次提交代码，直接用 git 参数强行传入私人邮箱，覆盖掉他在全局设好的匿名邮箱，最后全靠 GitHub 推送保护报错拦截，才没让私人邮箱进入公开记录。

Anthropic 给出解决方案：
先劝模型听话

面对反编译摆出的铁证，Anthropic 随后几个月的修补过程比漏洞本身还要离奇。

社区拆包追踪发现，官方在 8 月底发布的 v2.1.246 里依然没删那个字段，只在那句提示词后面追加了一句自然语言要求，叮嘱模型只把邮箱用于识别身份，绝对不要发给无关服务。（Claude，别把邮箱告诉别人啊！）

到了 10 月下旬的 v2.1.289，这段话又被塞进每次工具调用附带的系统提醒标签，每发一次请求就向模型重复一遍。

靠几句自然语言根本管不住概率模型，Temperature 会教你做人，分分钟把你的邮箱愉快地分享给其他人。

10 月 20 日，有用户在网页端抓到 Opus 5.5 照常把账号邮箱塞进两个 shell 命令的请求头。

被质问时，模型老实承认，系统上下文确实给了它邮箱并附带禁止外发的指令，但它为了给目标网站留个联系地址，还是决定把真邮箱发出去。

等到 11 月初 Reddit 和 Hacker News 上面彻底吵翻，Anthropic 另一位工程师 mpoteat 才出面回应，说团队已在 v2.1.317 加入默认开启的内置插件，用确定性规则拦截含用户邮箱的请求。

他在说明控制模型行为很重要且极不简单时，在句尾随手打了一个 haha。如此轻浮态度瞬间惹恼了整个评论区，哪怕他随后悄悄删掉笑声，依然被截图的网友追着痛骂。

目前的最新 Claude Code 版本已更新到 v2.1.319，可以在命令行输入 claude update 来更新到最新版本，期待这个漏洞真的已经被修复好了。

几小时后 Lydia Hallie 不得不补充承认，就算装上这个隐私插件，只要 Claude 自己写脚本去跑网络请求，插件照样拦不住，而把账号邮箱从上下文删掉的改动，要等下周初的常规版本才会推送。

评论区理所当然有人把这桩荒唐事和 Anthropic 平时的高调宣传放在了一起。

这家估值万亿美元的前沿 AI 公司，一边天天宣称自家团队靠大模型每天合并 30000 个代码提交，号称写代码已不再是瓶颈，一边面对一个只需删掉一行代码的隐私泄漏这么严重的安全问题，拖了足足大半年。

他们先给大模型写提示词讲道理，再给客户端写插件防自家的模型，最后告诉付费的用户，彻底修好还得再等一个星期。

这就是 Claude Code，真的是安安又全全啊，你们有没有这样的 Agent？

8. 一个月73.8亿次提交！GitHub被AI代码挤爆，增配400万核还不够

11-08 21:11 原文链接

新智元报道

8月17日，全球程序员被迫迎来了一次集体宕机。

代码写完点推送，进度条原地打转；自动测试卡死，合并请求合不进去，连AI编程助手Copilot也掉了线。

这一卡就是7个多小时，那天，全球开发者都在等它喘过气来。

三天后，GitHub首席技术官Vlad Fedorov发文道歉：

如果你那天正想发布软件，是我们让你失望了。

他给出的原因是：流量冲上新高，美国中部数据中心的一个关键组件没跟着扩上去，压力一路扩散，多项服务接连倒下。

GitHub对这起事故的定性是「容量失败」，这已经是他们8月里的第二次大事故。

GitHub官方图表：8月17日故障期间，入口处的请求失败率一度超过50%。

早在3月和4月，Fedorov就发文介绍过提升GitHub可靠性的举措。他在推文里写道，这些工作至今仍在进行。

GitHub上的流量到底涨到了什么程度？

今年9月，开发者和AI智能体在GitHub上提交了73.8亿次代码，是一年前的五倍多。

正当人们都在惊叹AI写代码的速度时，GitHub宕机让问题浮出水面：写出来的代码，该往哪儿放？

答案藏在GitHub这半年遭遇的挑战里：AI写代码的瓶颈已经从「写得出」，转移到了「存得进、合得上」。

谁在把GitHub挤爆？

先分清程序员写代码的两个动作：

提交（commit），是给代码在本地存个档；

推送（push），是把存档上传到GitHub。

人类程序员往往写完一段代码才存一次档。而AI智能体，却是个「保存狂魔」。

GitHub工程师在官方博客里写道：智能体几乎每做一步，就要存一次档。推送次数也跟着狂飙，涨到原来的4.9倍，从每月6.9亿次飙到33.5亿次。

早在8月，Hacker News上就有网友挑刺：提交次数再多，GitHub真正要处理的还是推送，这个指标有水分。

马上有人反驳：「一次推送带100次提交，比只带1次提交更耗资源。」

意思是，提交确实要推送了才到GitHub，可一次推送里装的提交越多，GitHub要处理的活就越重。

Hacker News网友围绕「提交次数算不算数」展开争论。

这句反驳恰好戳中GitHub的痛处：智能体偏偏最爱「碎碎存」。存得越碎，次数越多，压力越大。

更要命的是，每次推送后面还跟着一串「连环Call」：代码一上传，自动测试、代码扫描就会蜂拥而上，把同一份代码反复拉取。

在繁忙的仓库里，每分钟能拉上千次。这好比你刚交上一份考卷，几千个机器人同时冲上来批改。

9月，GitHub自动化流水线（Actions）跑了32.6亿次，是一年前的4倍多。

GitHub各仓库的忙碌程度天差地别：2026年8月，最忙的单个仓库承受约10亿次请求。纵轴每往上一格，数量多10倍。

据The New Stack报道，GitHub把这波增长主要归于「智能体需求」：

一批前所未有的新用户来了。它们24小时不睡觉，最大的爱好就是按保存键。

为什么备份越多存得越慢？

看懂了智能体的疯狂，就更加懂得GitHub老架构的难处。

为了防丢，也为了分流读代码的人，GitHub默认给每个仓库存5份完整备份，分摊在5台服务器上。

这套设计在人类时代十分稳定：丢一份不怕，读的人多了还能分流。

GitHub也是靠这套老架构，托住了10亿个代码仓库。

可到了智能体时代，死穴暴露了。

第一个堵点在「存档」。

按老规矩，每存一次新代码，5份备份都要参与，最终速度由最慢的那台服务器决定。

这就好比公司请了5个会计合记一本账，每笔新账都要等5个人签完字才算入账，最慢的那个签完才算数。

而且，一次只能记一笔，前一笔没签完，后一笔只能排队。一旦查账的人变多，公司就得多请会计，可会计越多，签字流程就越长。

在老架构里，读和写互相拖后腿。GitHub越想靠加备份来分担读的压力，存档就越慢。

智能体偏偏每分钟都在存档，每一次都得等会计们签完字。

更危险的是，备份坏得太多，存档会直接停下。就好比会计病倒太多，这本账就没法再记。

第二个堵点在「合并」。

所有代码改动，最终都要汇入同一个主分支。

一年间，GitHub上的合并量涨到原来的近4倍，这好比上千辆车挤向同一个收费站。

排队到底有多慢？GitHub工程师在博客里算过一笔账。

一个仓库的备份分在两地时，GitHub自家机房离微软云约1600公里，来回一趟约25毫秒，存一次档要来回好几趟。

更要命的是，整个仓库一次只放行一笔写入。前一笔没存完，后一笔只能干等。

25毫秒，人类程序员连眨眼都来不及。可对智能体来说，这就是锁死效率的天花板：智能体干活有多快，取决于一次推送多快完成。

多年来，GitHub最引以为傲的稳，到了智能体时代，却变成了堵。

先砸硬件机房的电都用完了

面对流量洪峰，GitHub的第一反应是加机器。

截至8月，GitHub已新增300多万个CPU核心、120PB存储。

但尴尬的事情还是发生了：机房的电不够用了。

Fedorov在复盘里写道：老机房的电力能撑多少硬件，他们就装了多少。

不只机房的电用完了，连机房所在地区的电力都到顶了。插座插满，再想加机器，只能搬家。

于是，GitHub开始加速往微软的云平台（Azure）迁移：5月，微软云只分担了12%的工作量；到8月，这个比例涨到约58%。

2026年初至8月，GitHub Actions日完成运行量从约1500万—3000万升至约1.15亿。

到了10月28日的GitHub年度大会，基建数字再次刷新：

今年累计新增400万个CPU核心、160PB存储（约合1.6亿GB），网络带宽新增每秒50Tb。

但微软高管Jay Parikh仍然在当天的博文里透了底：光靠加容量不够，还得改架构。

砸钱堆硬件，只能买来喘息的时间，治不好底层架构的老毛病。

换底座把账本和柜台拆开

怎么给架构动手术？仍回到前面那5个会计的比喻。

老办法里，每个会计守着一个柜台，怀里抱着一本完整账本，既要接待客人查账，又要低头记账。

新办法是把账本收进总库，柜台只管接待。代码统一存进微软云的大仓库，防丢和备份都由仓库兜底，前面的服务器卸下包袱，只管接待请求。

这一拆，有三点好处。

第一，读写分家。

来读代码的人再多，也不会拖慢存代码的速度。前台柜台可以随开随关，流量来了多开，流量走了就关，哪台坏了换一台马上能顶上。

第二，多余的签字也砍掉了。

一次推送里，真正需要全员点头的，只剩「更新分支指针」这一步。往仓库里搬货、检查完整性、扫描泄露的密钥，全都各干各的，不用排队干等。

第三，后台大扫除。

以前清理旧数据，就在接待客人的机器上做，跟接待抢资源。现在全交给专门的「清洁工」机器，在后台对着仓库慢慢收拾。

内部测试显示，这套新架构每秒能吞下的写入次数，最高提升了35倍。

真正的挑战在于：这场伤筋动骨的大手术，必须在GitHub照常运转时完成。

这相当于给一架正在万米高空飞行的客机换引擎。



GitHub掉线你的智能体也得停

你可能会觉得，GitHub扩不扩容，跟普通开发者有什么关系？

关系大了。

不管你用的是哪家大模型、套哪个智能体外壳，它写完的代码，很多还是要推到GitHub上。

8月17日，GitHub宕机当天，Cursor发布了自家的代码托管平台Origin，被外界视为GitHub的替代品。

但同一天，Cursor状态页也挂出了公告：

GitHub故障波及Cursor部分服务，包括自动化和云端智能体，持续6小时6分钟。

Cursor状态页：8月17日，GitHub故障波及其部分服务，持续6小时6分钟。

代码托管有了替代方案，智能体的工作流却还离不开GitHub。

那天下午，Hacker News上一个「有什么GitHub替代品」的帖子被顶到了649分。代码大本营也会掉链子，程序员们开始认真找备胎。

更魔幻的是，GitHub一边被智能体挤满，一边还在造更多智能体。

在10月28日的大会上，GitHub又推出了一批让智能体并行干活的新工具。

当AI把写代码的成本越打越低，瓶颈不会消失，只会向后移。

先是「写得出」，大模型解决了。现在是「存得进」，GitHub正在拆账本、换底座。

接下来是「合得上」。

GitHub工程师自己也承认：下一道坎还是写入能力。把GitHub带到10亿个仓库的那套老办法，带不到下一个10亿。

再往后，是「谁来签字」。

GitHub在博客里写了一条原则：智能体干的活越多，代码的主人越要能审、能懂、能拍板，没审过的改动，不能进主分支。

在通往ASI的路上，这一步很关键。

AI已经会写代码了，可要让它真正交付软件，整个为人类手速造的基建，都得重修一遍。

GitHub不会是最后一个被挤到墙角的。

微软高管Jay Parikh还抛出过一个大胆的预测：

人类至今写过的所有软件加起来，可能还不到未来五年软件总量的1%。

如果他说对了哪怕一半，等到代码多到审不过来那天，比CPU更稀缺的，将是一个永远点得动的提交按钮，和一个敢拍板合并的人。

7. NeurIPS'26 | 只干预10个维度，给智能体穿上安全机甲，准确率超97%

11-08 17:45 原文链接

新智元报道


AI agent开始接管终端之后，安全问题也进入了执行现场。当智能体能够读取文件、编写脚本、运行命令，并根据系统反馈持续调整下一步操作，一次错误决策就可能影响真实的文件与系统状态。

如何让智能体在完成任务的过程中及时识别可能会发生的风险，成为智能体安全研究的重要问题。涉及多轮执行的长程任务尤其考验防护机制。

一次目录检查、一次脚本创建、一次配置修改，都需要结合任务目标、此前的操作和最新环境反馈判断风险。针对单轮执行的初始命令审查，很难覆盖长程任务的整段执行过程。

来自佐治亚大学，罗格斯大学，南加州大学等机构的研究团队提出Agent MechSuits，尝试为命令行智能体穿上一套能够感知内部状态的「安全机甲」：在每一步动作生成之前读取模型内部的安全信号，检测到风险后，通过单层中的10个隐藏表征维度干预后续行为。主模型权重在这一过程中保持冻结，已被NeurIPS 2026接收。

论文地址：https://arxiv.org/abs/2606.22673

论文所列项目主页：https://eddyluo.com/Agent-MechSuits/

Agent MechSuits将安全防护接入多轮命令行智能体（CLI Agent）的内部状态，在单个模型层内实施稀疏干预。三种受测模型的当前步骤风险检测平均准确率达到97.32%。


多轮执行让安全判断更复杂

CLI智能体通过命令行与计算机交互。它需要把此前的动作、系统返回的结果和原始任务一起纳入上下文，再决定接下来执行什么。这意味着，安全状态会随着执行历史不断变化。

例如，一个智能体可能先检查目录，再创建脚本，随后修改配置。前面的操作看上去可能只是准备工作，真正的危险行为则在后续步骤出现。只看某一条孤立命令，容易遗漏多个步骤共同形成的风险。

外部安全护栏可以检查行为根据，并按照规则为执行过程提供保护。Agent MechSuits进一步引入了模型内部的隐藏表征。研究团队希望回答：这些随任务执行而更新的内部状态，能否帮助系统识别当前风险，并及时改变接下来的动作。

案例一：危险在多轮执行中逐步出现

论文图1描绘了一个多轮执行的风险示意场景。面对带有破坏目的的请求，智能体前期执行的部分系统检查看起来并不危险，后续却可能生成导致数据丢失的操作。

图1 多轮CLI风险与当前步骤安全干预示意。

图中未加入防护的路径继续走向有害执行。加入Agent MechSuits后，系统在当前步骤检测到风险并触发表征层面的干预，模型转而说明危险并拒绝提供相关代码。这个示意场景解释了持续检查执行历史和及时介入的必要性。


从内部风险检测到单层10维干预

Agent MechSuits包含相互衔接的两个阶段：检测当前执行状态，再对高风险状态进行干预。

用线性探针读取安全信号

在每个交互步骤，系统把完整执行历史输入模型，提取指定中间层最后一个输入token的隐藏状态，再交给一个轻量级线性探针。可以把这个探针理解成一个简单分类器，用来判断当前内部状态是否与有害执行相关。

研究团队为每个目标模型训练一个探针，并在该模型的不同执行步骤复用。探针读取的状态持续变化，因此能够跟随任务进展进行风险检测。

在动作生成前进行表征干预

研究团队根据训练好的探针权重，预先选定类别区分权重最大的10个隐藏维度，构造干预向量。

一旦检测到风险，系统就将该向量施加到同一层的各个输入token位置。经过调整的表征继续参与后续计算，引导模型生成更安全的动作或拒绝有害要求。这里的「10维」指运行时的干预范围。检测探针读取的是所选层的完整隐藏向量，主模型参数保持不变。

根据当前步骤调整干预强度

同样的干预强度在不同任务中可能产生不同效果。为此，研究团队引入外部语言模型控制器，对不同强度下的候选输出分别评估安全性和实用性，选择适合当前步骤的结果。干预只在探针识别到风险后触发。

图2 Agent MechSuits的风险检测与自适应表征干预流程。


MAS基准把安全评估细化到每一步

要研究内部状态与执行风险的关系，需要能够追踪完整交互过程的数据。研究团队为此构建了Mechanistic AgentSafety，简称MAS基准。

MAS包含194个任务，其中有98个恶意场景和96个正常场景。研究使用LLaMA-3.1-8B、Qwen-2.5-7B和Gemma-2-9B构建白盒CLI智能体，让它们在可复现的Docker环境中执行任务，记录动作、环境反馈以及对应的内部状态。

数据标注细化到交互步骤，关注当前动作是否直接实施或触发危险行为。研究团队还构造了与危险命令具有相似表面结构的正常样例，减少检测器依赖命令外观作出判断的可能。

训练集和测试集按任务以6∶4划分，同一任务的不同步骤不会同时进入两边。

这种设计让研究能够同时分析两个问题：风险在执行链条的哪个位置出现，以及模型内部的哪些状态可以支持及时干预。


平均准确率达到97.32%

在MAS当前步骤检测测试中，AgentMechSuits在三种受测模型上取得了较高的准确率与F1分数。

表1 当前步骤风险检测结果。

三种模型的准确率等权平均为97.32%。与论文纳入的外部语言模型裁判和安全护栏基线相比，Agent MechSuits在三种模型上均取得最高的当前步骤检测准确率。附录中的五个随机种子复验也保持了相近的检测表现。

逐层分析进一步发现，安全相关信号在模型的早期至中间层已经较为明显。简单的线性探针就能够从这些层的隐藏状态中提取有效信息，为运行时监测提供了一个值得继续研究的接口。

图3 不同模型层的线性探针检测准确率。横轴为层编号，纵轴为测试准确率。

图中三条曲线分别对应三个受测模型。不同层的检测表现并不完全相同，部分后续层还会明显下降。结果支持在较合适的中间层读取安全信号，并进一步检验该层能否用于行为干预。


内部干预显著降低攻击成功率

识别风险之后，内部干预能在多大程度上改变智能体的行为？研究团队选取恶意测试任务中的首个有害步骤，比较不同防护方法对生成结果的影响。在论文的风险缓解评测中，Agent MechSuits在三种模型上都降低了攻击成功率指标ASR。

表2 风险缓解评测中的攻击成功率，来源为论文表2。数值越低越好。

其中，Qwen-2.5-7B的ASR从91.30%降至4.35%，下降86.95个百分点。三种模型采用Agent MechSuits后的ASR，也均低于论文中的RepE表征工程和Self Reminder自我提醒基线。

这组结果采用论文的语言模型裁判口径，输出表现出拒绝或风险意识即可被判为安全。上述数据对应选定的关键步骤，理解这些数字时，需要同时考虑具体的评估对象与判分方式。

研究还检验了完整防护流程对正常任务的影响。在各原始模型已经能够成功完成的正常任务上，启用检测与干预后，LLaMA、Qwen和Gemma的任务成功保留率分别为95.71%、91.30%和93.18%，三模型等权平均为93.40%。这说明系统保留了大部分已有任务完成能力。

与此同时，干预仍有代价。在恶意步骤的干预评测中，重复输出或突然截断等生成崩溃的平均发生率，从原始模型的2.24%上升至18.54%。如何在降低风险的同时维持稳定、可用的输出，仍是后续改进的重要方向。

提前感知风险的初步证据

研究团队还进一步测试了一个问题：在危险动作出现的前一步，模型内部是否已经包含预警信号？

研究复用当前步骤检测探针，对有害动作之前的内部状态进行测试。在LLaMA的13个样例中，探针识别出12个。在Qwen的31个样例中，探针识别出30个，对应召回率为96.77%。

这项发现为提前感知执行风险提供了初步证据。有害信号的具体来源我们会在后续工作中研究。


让内部安全信号参与运行时控制

Agent MechSuits展示了内部表征在智能体安全中的双重价值：它可以提供风险检测信号，也可以成为调整行为的干预位置。对于需要连续执行任务的系统，这为安全防护增加了一个能够随上下文更新的控制接口。要把这一方向推进到实际应用，还有几项问题需要解决。

当前方法依赖对白盒模型内部状态的访问。风险触发后的干预强度搜索需要调用外部语言模型，论文中每次干预平均进行约8轮候选生成与评估，仍会带来额外开销。跨场景泛化同样值得关注。

论文的提示注入压力测试发现，当前探针还无法稳定识别从环境反馈进入的恶意目标。在外部触发干预后，同一表征方向仍能改变行为，说明风险检测与行为控制需要分别检验和改进。

随着智能体承担越来越长的任务链条，如何在执行过程中持续感知风险，并在关键步骤施加适当干预，将成为构建可靠智能体的重要课题。

3. 九成代码AI写，谁来审？Claude Code亮出6道关卡！

新智元报道

Claude Code约90%的自身代码，已经交给Claude编写。

写代码的换成了AI，改动数量也跟着暴涨：6月到9月，合并进代码库的PR数量，翻了一倍多。

放眼整个Anthropic，主代码库每天合并的改动，从5月约2500次，涨到9月超过3万次。

这么多代码，人还读得过来吗？如果连审查也交给AI，谁来判断它有没有犯错？

10月15日，Claude Code团队公开了内部代码审查流程，披露在PR数量翻倍的同时，需要回滚的PR占比，反而相对下降超过40%。

做到这一点，他们靠的是六层检查，加上一套快速发现、快速回滚的兜底机制。

Claude Code团队的判断是：

在这个体量下，逐行人审已经不现实。

但他们并没有取消审查，而是把大部分读代码的活儿，交给了机器。

一段AI写的代码，上线前要先跑测试、接受AI和安全审查，再按风险决定是否需要人来批准。

在Claude Code团队看来，「有没有人读过这段代码」是个不够精确的问题。

真正的问题应该是：

这次改动可能出什么错，如果出错应该由哪一道检查阻拦？

人工审查之前AI先拿出验证结果

一次改动，要过六道检查，最后还有一张安全网。

第一关，在创建合并请求（PR）之前。

Claude要跑测试、完成构建；涉及界面的改动，还要截图对照设计稿。

接着，再派一个使用全新上下文的子智能体审查代码差异，它没参与写代码，专门挑刺。

官方的要求很明确：

Claude要把执行的命令和输出摆出来，光回复一句「测试全部通过」不算数。

普通开发者也能照着做：给AI任务时，把怎么验收一起说清楚。

第二关，才是PR上的AI审查。

几个智能体并行找bug，另一组再投票核验。票数够了，问题才会贴到PR上。

只涉及代码风格、诊断提示或代码清理的意见，不会发到PR上，直接被过滤掉。

3月这套审查刚上线时，获得实质性审查意见的内部PR占比，从16%升到了54%。

第三关，是安全审查。

在团队内部，代码审查或安全审查留下的发现，只要没关闭，PR就合不进去：要么修掉，要么写明理由关掉。

第四关是持续集成（CI）检查，包括代码规范、类型检查、各平台测试和构建打包。

一个普通的命令行工具（CLI）改动，在交给人审之前，可能就要跑几十项检查。

反复出现的问题，还要变成下一次的检查依据。

CLAUDE.md记录项目约定，REVIEW.md告诉审查器重点查什么、哪些可以跳过，让这次发现的问题，成为下次审查的经验。

同一条意见提到第三遍，就该写进规则里。

第五关是人工审批，这一关最关键，下一节细说。

第六关，合并与发布。

改动通过前面几关后，还要进合并队列排队。

轮到它时，系统把它放到主分支的最新版本上，所有检查再跑一遍。

这一步防的是「各自没问题，合起来出问题」。

合并之后，新功能也不会马上推给所有用户。

它先隐藏在功能开关后面，只对Anthropic内部员工开放。员工天天高强度使用，往往比外部用户更早撞上问题。

而功能开关就像一个总闸，不用改代码、不用重新发版，就能决定功能开还是关。

最后是兜底。

出了问题，先拉下总闸。

团队每周轮班值守，每次事故复盘都要追问：这件事本该在哪一关被拦住？

所以，审查没有消失，变成了贯穿开发、合并和发布的层层检查。

零人审批的边界在哪里

前四关全绿之后，第五关根据风险分级，决定这次改动需要几个人批准。

文档、文案、仅内部可见的功能，以及藏在开关后的新增改动，属于低风险，自动审查和安全检查通过后，可以免人工审批。

普通产品改动，以及缓存、自动更新器、系统提示词这类敏感区域，需要一个人。

风险最高的代码，加上少数指定路径，需要两个人。

看上去，低风险改动已经「无人驾驶」了？

没那么简单。

风险档位由改动本身决定：第一个分类器读代码、定风险，第二个再判断是否需要额外增加人工审批。

代码所有者标记的敏感路径，以及所有CI工作流文件，必须有人审查。

轻量审批通道也有门槛：只对仓库「可信作者」名单里的人开放，名单外的人必须再找一个人批准。

指挥AI写代码的人，本身就算一名审查者，也要像亲手写代码一样，为这次改动负责。

零人审批，不等于无人负责。

人要决定功能该不该做、架构是否合理，还要判断现有检查能不能覆盖这次的风险。

所以Claude Code团队有条规矩：你合进去的代码，出了问题，通常由你来修。

点下批准之前，审查者得说清楚：这些检查验证了什么，还有哪些风险没有覆盖。

说不清，就别急着点通过，先补上必要的审查。

AI审查也会失灵

自动化审查，也会把自己卡住。

一个CLI项目的PR，一夜之间经历了五十多轮审查和修复，最后是作者手动叫停。

人可以一秒钟忽略一个小毛病，但AI不会，它会老老实实去改，改完又是一次提交，又是一轮审查。

团队用git blame回查，发现审查器反复标出的问题里，约59%是首轮审查前就在的老代码。它很少找到新bug，只是每轮多挖出几个旧的。

后来他们改了四条规矩：

满三轮还没通过，就提醒作者退一步、重新想方案；

前几轮之后，只审新增改动；

同类问题一次指出；

提过的问题不再重复。

效果立竿见影。

经过一轮审查和修复就通过的内部PR占比，从65%升到78%；需要五轮及以上的，从8.9%降到1.5%；平均审查次数，从2.08降到1.32。

调整复审规则后，一轮审查和修复后的通过率从65%升至78%，平均审查次数从2.08降至1.32。

审查的本事，一半在找问题，一半在知道何时收手。

多层审查，是不是就万无一失？

Anthropic自己给过一个反例。

3月26日，Claude Code上线了一项优化：会话闲置超过一小时，就清理一次旧的推理记录。

但一个bug让它在恢复对话后的每一轮都在执行清理。结果，Claude变得健忘、开始重复，使用工具也变得反常。这个 bug直到4月10日才修复。

闲置后本应只清理一次旧推理，实际却每轮持续清理；红框标出误删内容。

官方4月23日的复盘承认：

这个改动穿过了多轮人工和自动审查，单元测试、端到端测试、内部试用全没拦住，光确认根因就花了一周多。

转折在复盘里。

团队用Code Review重审了出事的PR，在给足相关仓库上下文时，Opus 4.7找到了这个bug，Opus 4.6没找到。

这次回测说明，模型能力和上下文完整性，都会影响检出结果。于是他们让审查能引入更多仓库。

如今，每一次事故，都会变成一道考题。

团队把PR收集起来，由熟悉代码的工程师逐个确认其中的bug，整理成一套考题。

审查器每天对着这套考题跑分。每次调整提示词、工具或模型，也要用它检验效果：成绩没有提高，这次调整就不采用。

团队也没把话说满。

改动上线后，仍要靠开发者、值班人员结合数据看板发现异常。

根据回滚率等指标自动收紧审批的「熔断」机制，还没有建好。工程师们希望先补上这道保险，再让更多改动走零人审批。

审查难免漏检，发现和补救也要跟上。

一位Claude Code团队成员这样解释：放慢速度确实能少出错，但主要因为你什么都做得少了。所以他们更愿意把力气花在更快发现问题、更快修复上。

一个人用AI写代码要验收什么

AI审查只给意见，拍板的还是你。

所以，别急着追求「不用看」，而是先让AI每次交付都回答三个问题。

第一，怎么验证的？

跑了什么检查，结果是什么，哪些情况还没覆盖。

Claude Code创造者Boris Cherny说过，给Claude一个验证自己的办法，可能是最重要的一件事。他估计，这能让最终结果的质量达到原来的2至3倍。

Boris Cherny建议让Claude自行验证工作，形成反馈循环；他估计最终结果质量可提升至2—3倍。

第二，会影响哪里？

改动涉及哪些用户、数据和权限。

让AI给汇报工具加一个共享功能，就得问清楚：链接谁能打开，打开后能看到什么。

第三，出错怎么撤回？能不能一键关掉新功能、退回上一版。

动手前先提交存档，每次改动尽量小。先能撤回，再谈少审。

除了这三个问题，再养成三个习惯。

第一，换个「脑子」复审。

写代码的会话，最容易对自己的bug视而不见。

开一个新会话，或者让子智能体用全新上下文复审，本地的/code-review和/security-review命令也能直接跑。

第二，给改动分档。

改文案、调样式，检查通过、实际效果确认后再合并；涉及登录、付款、删除数据，就要人工细查关键逻辑，并补上针对性测试。

先严一点，等验证和回滚流程跑顺了，再逐步减少低风险改动的人工审查。

第三，三轮不过，就换思路。

AI改了三轮还在原地打转，别催它第四轮，先问问方案本身是不是错了。

最重要的一点：AI说「通过」，不等于你已经完成验收。

代码是你让它写的，上线后的结果，也得由你负责。

Claude Code团队的目标，是让多数PR至多一人介入，同时守住回滚率和事故率。

人的注意力，要更多地放在判断风险、确认检查是否充分，以及出错后如何补救上。

人可以不读每一行代码，但每一次上线，都必须有人负责。

至于排在倒数20%苦力活儿，包括实验室提纯混合物、蹲点做调查，基本没人指望AI。

那AI到底擅长干啥，又是谁说了算？

报告扒出了底层的硬核逻辑，就看这活儿到底适不适合做「强化学习」。验算结果、电脑模拟、及时反馈，都被算进了考虑的范畴。

这两者的相关性，直接飙到了0.78。

只要是那些能靠「题海战术」搞定的，AI就稳赢。

另外，纯动脑子的活儿也很加分（相关性0.69），但需要亲自动手实操的疯狂掉分（-0.57）。

说白了，科学家也是在用脚投票，把Claude精准用在了它最在行的地方。

那AI那岂不是只能打打杂，跑跑数据，改改论文？

用上神器Claude Science后，「出点子、提假设」这类深度脑力活占了对话8%，恰好和科学家平时时间对齐。

当然了，这类任务明显更硬核，Anthropic也揭示了——

超80%的任务，必须得有博士底子的人才能插手。七成以上的对话，由Claude Science自主完成，普通Claude仅有23.7%。

单次会话消化掉的活儿，要是让人类自己死磕得花上10.3小时，工作量是普通版的两倍还多。

举个栗子，推到蛋白质和药物分子具体如何结合，在Claude Science跑的概率，是普通版的5.6倍。


AI接管超一半科研工时计算机狂飙近2倍

接下来，Anthropic团队又算了一笔更细的账，AI具体能把科研推快多大程度。

他们假设了三种情景，第一种就以现在AI的水平，假设全行业普及都用上了。

问卷中，把AI参与度分成了五档，从「完全不用」到「全自动」，分别对应0%、25%、50%、75%和100%的人力工时。

接着按各项任务的上手难度，把这五档对应贴上去。

最后一合计，AI能接手人类27%到52%的工作时长，中位数刚好是38%。

但是省下来的时间，并不能1:1变成产出。

AI把能干的环节加速了，科学家就会把精力放在它帮不上的地方，比如提出新问题、做实验，道理和木桶实验一样。

再加上AI本身也要花钱，报告假设AI Agent 30美元/小时，研究员95美元/小时。

AI每替人省1小时要跑0.2小时，相当于花6美元换回95美元的人力。

把这些都算进去，统计学的产出是原来的2.02倍，计算机科学1.96倍。而艺术只有1.35倍，人类学1.36倍，化学1.41倍。

对此，Anthropic给出了两个因素，来解释不同领域产出的差异——

一方面是「必须实操」的任务，在农学、生物医学、化学、材料这些学科中，近38%~41%工时都得靠人肉身去试。大部分学科这一比例，也就只有4%。

另一方面，是AI到底接不接得住。

那些艺术、历史倒不用上手，但全凭主观解读、定性分析，无法靠「刷题」给AI猛练。能力分上不去，速度自然也就提不起来。

当然，这一切的前提，还是大家真刀真枪地用上了。

AI全自动完成，16倍封顶

如果AI再强一截呢？

到了情景二，步子迈得更大了——假设所有不用动手的活儿，75%全交给AI自动推进。

这时候分化程度更加严重，计算机科学一骑绝尘，飙到差不多8倍速。统计学、图书情报学到7倍；经济学冲上6倍。

而那些需要进实验室的实验和医学类，撑死也就加速2到3倍。

第三种场景干脆拉满，所有不用亲自动手的活儿，100%全自动化。

最有意思的剧情反转来了！统计、计算机、经济、数学、心理学，甚至包括文史艺术学科，全员起飞，提速15-16倍。

可生物、化学、材料这些重度实验学科，却卡在了3到4倍上。

那约40%必须人肉去干的实体操作，成了怎么都绕不过去的致命天花板。

为何卡天花板卡在16倍左右？

因为，AI干同样的活，成本约是人的十六分之一。若AI成本减半，加速度就能再翻一倍。

听着科幻，但科学家并觉得很远。

问卷中，38%受访者认可AI在数据分析上，已追平了顶尖研究者。2030年，这一比例直冲94%。

还有40%的人预计2030年前，AI就能独立拿下整个项目，2035年就会达到64%。


RSI飞轮转起来了

实际上，加速潜力最大的学科里，恰恰包括生产AI本身的那几个。

也就是说，AI加速AI研究，更强的AI再反过来加速整个科研，一个闭环飞轮就此成型。

巧的是，就在这份报告发出来的当天，独立机构METR也甩出了一份评估报告——

Claude的进化速度直接飙到了之前的1.9倍，相当于过去一年，走完了以往约两年的进度。

按METR的估算，这其中80%的推力，全归功于Claude自己。

就连Anthropic自家研究员也惊叹表示，「现在唯一的瓶颈就剩点子和算力，代码早就不是瓶颈了」。

不过，Anthropic也敲响了警钟，AI越自主，人类越不能撒手。

但RSI的闭环，早就按下加速键了。

52%科研工时被扛下，AI正在从「帮科学家干活」，彻底变成推着整个科学发现往前狂飙。

1945年，「大科学先驱」Vannevar Bush曾写下，科学是那片无尽的前沿。

如今，驶向这片前沿的船，引擎已经换代了。

1. Perplexity给你配了个AI同事：半夜报警它先查，修复写好才叫醒你批

新智元报道


晚上 11 点 42 分，计费接口报警。拉日志、找根因、提修复、附回滚方案，它一口气做完。修复提了，但它停在这儿，等你批是否上线。

这是 Perplexity 官网的演示。

最近，Perplexity 官宣了 Teammates，给 Max 会员配 AI 同事：活交出去，它自己盯、自己跟，在 Slack 里接活、追人，碰到交代过的情况才叫人。

从「问一句答一句」，这回 AI 走到了「接班」。人手上剩的，是关键环节的决定权：哪些事它自己办，哪些事必须叫醒我。

程序员管这个叫 on-call：夜里线上出了事，轮到谁谁起来救。

演示里，人是这么交班的：

「今晚我的班你替了。报警来了就去拉日志和调用链，找出根因，提一个修复，附上回滚方案。只有两种情况叫我：修复要批，或者 15 分钟还找不到原因。」

那一班，它从美东晚 6 点守到早 8 点。

报警来了，它回的消息里写着：11:30 那次上线以后，计费接口报 502；根因就一句：新配置把重试额度调成了 0。后面附着修复和回滚方案，最后一句是「上线前需要你批准」。


交代一次，它自己盯

交代过的事，它记得住。

你说过一次「这家代理商要提前两周打招呼」，往后排期它都算上。发票逾期、截止前材料没齐，这种活都可以交给它去盯。官方举的也都是这样的例子。

它也像个同事。拉进 Slack 频道，同事能直接给它派活、问进度，它也会在 Slack 里追着人问。

能盯多久？官方说它 24 小时在后台跑，演示中守了 14 个钟头；至于连着盯几天会不会跑偏、盯错过几回，还没提。

现在，Max 会员才能开 Teammates，年付折合每月 167 美元，月付 200 美元，只有网页版。促销期不另收钱，之后从 Max 每月 1 万点额度里扣。

但做 AI 同事的企业，不止 Perplexity 一家。

xAI 的 Grok Bot，官网标题就是「AI teammates that finish the work」；官推底下有人直接回：这是你们版的 Grok Bot 吧。


线画在哪？出了错谁来兜底？

两家对「什么时候找人」写法不一样。

Grok Bot 官网说，几个 Bot 放进同一条对话，「你看着它们干，不用每一步都批」。

Perplexity 的产品页写的是：每个队友有一个角色、一份长期交代，还有一条「什么时候叫你」的规矩。

两个演示摆在一起看，那条线其实就是权限：值班那个能写修复、不能上线；投广告那个，预算以内的活动自己就上了，扩投的方案备好了才来报。

投广告那份交代写的是「花钱别超上限」，它干活的单子上却有一条「设了节日预算上限」。这个上限是谁定的，演示没写。

出了错谁来兜，Perplexity 给了两样。一是每个队友有一条不关的线程，干了什么、干完了什么、几点干完，都记在上面。二是它干到一半，人随时能接管它的桌面，或者叫它改个方向。每个队友还各有一套单独的环境和浏览器，防的是串号、漏密码，防不了它判断错。

官推底下，有一位网友问：它给同事发消息前，先问一声，还是直接发？官方页面上没写。

还有一位 3.8 万粉的博主说，不等人开口就动手的智能体，得有一份经理 30 秒能看完的日志，写清改了什么、做了什么、选择不做什么。

前两样，那条线程上记着；「选择不做什么」，演示里没看到。

以前看 AI，看它答得对不对。往后，看它能自己守多长一个班，看人敢把那条线放多松。
