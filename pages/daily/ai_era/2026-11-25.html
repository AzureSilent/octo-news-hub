7. 具身评测提速约16倍：上交发布一站式评测工具RoboScopeKit

11-25 17:38 原文链接

新智元报道


视觉-语言-动作（VLA）模型的研发高度依赖仿真评测。无论是比较两个训练检查点、切换随机种子，还是观察训练中途的泛化表现，研发人员都要在LIBERO、RoboTwin、CALVIN、RoboCasa、RoboDojo等仿真Benchmark上，把几百到几千个回合完整重跑一遍。

在实际研发闭环中，这一评测环节主要面临两个瓶颈：

1、对接繁琐。每个Benchmark都有独立的启动脚本、相机命名、观测格式与动作约定，每个模型家族又带着各自的预处理与推理流程。要把多个模型放到多个Benchmark上横向对比，每一对组合都得单独编写和维护一份适配代码，换一个环境就要重来一次。

2、等待漫长。以公开的StarVLA检查点为例，按官方评测流程，单张RTX 4090跑完500个LIBERO-Long回合需要49.8分钟；换到RoboTwin Easy，单张RTX 4090跑500个回合需要7.0小时。按标准协议跑满5,000个回合（50任务×100回合），哪怕动用四张RTX PRO 5000并行，也要连续跑上17.5小时——傍晚提交任务，等到第二天中午才能拿到结果。


RoboScope Kit一站式具身评测工具

上海交通大学人工智能学院MINT实验室（赵波团队）在arXiv发布技术报告，推出一站式具身评测工具RoboScope Kit（下称Kit）。

研究者为模型写一个Python类，就能在所有提供其所需观测的Benchmark上评测；Kit的适配器已覆盖10+个主流仿真Benchmark，包括LIBERO、LIBERO-Plus、LIBERO-Pro、RoboTwin 2.0、RoboDojo、CALVIN、RoboCasa GR-1 Tabletop、RoboCasa365、SimplerEnv、MetaWorld MT50、RLBench、robomimic等，并可持续扩展。

项目主页：https://mint-sjtu.github.io/RoboScope-Kit/

MINT实验室：https://mint-sjtu.github.io/

代码链接：https://github.com/MINT-SJTU/RoboScope-Kit

按纯评测时间统计，Kit在三组核心测试中的表现如下：

• LIBERO-Long 500回合（单张RTX 4090）：比StarVLA官方评测快6.2倍，开启CUDA MPS后耗时从49.8分钟降至8.1分钟，比RLinf快3.8倍、比vla-eval快2.1倍。

• RoboTwin Easy 500回合（单张RTX 4090）：比StarVLA官方评测快13.2倍，耗时从7.0小时降至31.9分钟，比vla-eval快7.3倍、比RLinf快2.2倍。

• RoboTwin Easy 5,000回合标准协议（四张RTX PRO 5000）：比StarVLA官方评测快15.8倍，耗时从17.5小时缩短至66.4分钟，全部5,000个回合的成败与终止步数与官方评测一致。

RoboScope Kit系统总览：模型检查点与Benchmark套件接入统一的评测运行时


一次接入，处处可评

Kit把每个模型封装成一个Policy类：加载检查点、保留模型自带预处理，并声明三件事——需要什么观测、一次输出几步动作、隔几步读一次新观测。

每个Benchmark通过适配器接入，任务定义、初始状态、终止条件和打分继续由Benchmark自带评测器执行。评测前Kit自动核对两端接口是否匹配，运行中逐条检查观测和动作的类型与维度，避免静默跑错。

每个模型和每个Benchmark各接入一次，M个模型、N个Benchmark的对接从M×N份减少到M+N份。下面是Kit仓库中的UserPolicy示例，以LIBERO的libero_10为例：

import numpy as np
from roboscope_kit import ActionChunk, BenchmarkName, Policy, PolicyCapabilities, run
class UserPolicy(Policy):def load(self, context):self.model = load_model(context.checkpoint_path)return PolicyCapabilities( supported_benchmarks=(BenchmarkName.LIBERO,), required_features=("images.primary", "state.proprioception"), supported_suites={BenchmarkName.LIBERO: ("libero_10",)}, supported_action_chunk_sizes=(1,), )
def act(self, observation):return ActionChunk(np.asarray(self.model.predict(observation.features), dtype=np.float32))
if __name__ == "__main__": run(UserPolicy())

示例中的load_model和model.predict代表模型自己的加载与推理方法，接入时需要按实际模型实现。

接入其他Benchmark时，Policy只需声明支持范围。新增一个Benchmark只需补充适配器、任务套件清单和环境构建脚本，已有Policy不用改动就能直接评测。

有些模型推理时要记住上一步状态（比如X-VLA需要读入上一段动作的末端位姿）。Kit支持按回合编号（episode_id）隔离保存状态，同一个模型实例就能同时服务多个并发回合且互不干扰。


两种加速方法运行时优化和调度

面对动辄七八个小时甚至跨夜的评测，大家最先想到的往往是模型推理太慢，但打开显卡监控一看，RTX 4090大部分时间几乎处于闲置状态。团队顺着评测链路把每一毫秒拆开计时，找到了两处主要瓶颈：

1、评测流程在做重复工作。

在单张RTX PRO 5000上剖析StarVLA的RoboTwin官方评测（100个回合），每个回合都重建仿真引擎和渲染器，并先用专家轨迹校验种子（占6.9%），场景搭建占5.2%，按任务重启策略服务还额外增加5.3%墙钟时间；控制循环在每个物理步内重复求解相同的被动力。

更重要的是，主流VLA一次输出一段动作，RoboTwin上的StarVLA检查点一次输出16步，官方评测器却每一步都渲染4路相机画面（单次渲染约42毫秒，占评测器时间的43.5%），而模型只读取其中3路，且每16帧里只读1帧——100个回合共渲染37,064次观测，只有2,346次被策略读取，93.7%的渲染从未被使用。

2、硬件在空转。

StarVLA自带的LIBERO评测里，一个仿真进程和一个模型轮流执行。仿真和每一步的观测、动作处理在CPU上占评测器55%的时间，这期间模型在等待；模型推理时仿真进程在等待。一次推理55毫秒，其中GPU执行计算的时间为26毫秒，整个评测中GPU平均利用率为14.3%。

Kit用两种方法分别解决：运行时优化去掉单次评测进程内部的多余开销，调度让CPU和GPU并行工作。

方法一：运行时优化

Kit针对RoboTwin评测流程内部的运行开销做了一系列优化：

复用仿真引擎和渲染器。每个评测进程只创建一次SAPIEN引擎和渲染器，供它运行的所有回合使用；在5,000回合等长运行中，释放已完成任务的场景显存以防显存耗尽。

跳过重复的专家校验，按需加载运动规划器（cuRobo）。RoboTwin官方评测在每个回合开始前，会先跑一遍专家演示来校验随机种子是否可解，为此还要启动较重的运动规划器cuRobo。

Kit直接读取预先校验好的种子缓存，省去每次的专家校验；在此基础上，关节角控制本身不需要运动规划，Kit直接跳过cuRobo初始化（在三回合对照实验中，准备时间从45.2秒降到1.4秒），而末端位姿控制仍需运动规划，改为每个评测进程复用同一个cuRobo规划器，避免反复初始化。

精简控制循环。官方控制循环在每个物理步内重复计算相同的被动力，Kit把这份冗余求解合并为一次。

动作边界观测与按需相机渲染。模型一次输出16步动作，只在第1步读取观测。Policy把观测步长声明为16后，Kit只在每段动作的边界渲染新观测，物理仿真、动作执行和成功判定仍按原生频率逐步进行；在单卡对照实验中，渲染的画面从2,100帧减少到132帧，吞吐提升2.5倍。同时，Kit只渲染策略实际读取的3路相机（跳过未使用的前置相机，图像与官方逐比特一致）。

动作块长为16步时，RoboTwin官方评测器每步渲染4路相机，93.7%的观测从未被策略读取

为了剥离模型推理耗时、单独看运行时优化的收益，团队在一张RTX 4090上用不跑推理的占位策略逐项叠加上述改动，RoboTwin吞吐从每秒8.88步升到32.38步（3.6倍）。

在四张RTX PRO 5000（4个仿真进程、4个模型副本，下称K4/g4）上用真实的StarVLA模型评测100个RoboTwin Easy回合，上述运行时优化合起来把评测时间从1,349秒缩短到552秒（快2.4倍），每个回合的成败和终止步数都与官方一致。

RoboTwin单卡运行时优化逐项叠加的吞吐（使用不跑推理的占位策略）

方法二：调度

仿真和推理分开扩展。Kit把仿真进程和模型拆成两个独立的资源池：仿真进程（数量记为K）按CPU核数扩展，模型副本（数量记为g）按GPU显存和算力扩展，多个仿真进程共享同一个模型副本。

仿真进程和模型副本各自独立运行，Benchmark和模型可以使用各自的Python环境；不论运行多少个仿真进程，显存里只放g份模型。

不同仿真器和模型副本数量的运行时间线

时间线按剖析参数生成；图中的时间和利用率来自LIBERO-Long的50回合实测。

在完整500回合的LIBERO-Long评测中（单张RTX 4090），12个仿真进程共用1个模型副本时，GPU平均利用率为46.3%；加上第二个副本，利用率升到87.7%，评测时间从1,216秒缩短到748秒（快1.6倍），显存峰值为25.0GiB。

并发数自动选（Autotuning）。仿真进程和模型副本的数量需要联合确定：进程太少无法充分利用显卡算力，过多则会竞争CPU资源或导致显存溢出。只放1个模型副本时，仿真进程增加到4个后吞吐便停留在每秒112–114步；加到2个副本后，K12/g2的吞吐达到K1/g1的4.8倍，K16/g4进一步达到5.3倍。

最优配置随模型、Benchmark和机器变化。Kit内置的并发搜索通过真实任务进行短时探测，自动找到最快的K/g组合，并在预测显存不足时自动下调并发数。

在LIBERO-Long上，Kit只探测7组配置（对比18组完整网格搜索），不开MPS时选出K12/g3（距网格最快差1.2%），开启CUDA MPS后直接命中网格最快的K16/g4；在四张RTX PRO 5000的RoboTwin Easy上，搜索自动选出K60/g8。

一个模型副本时，仿真进程加到4个后吞吐不再增长；12个仿真进程配2个副本的吞吐达到K1/g1的4.8倍

多GPU、多实例一起跑。

一台机器有多张GPU时，Kit可以把模型副本分布到不同GPU（例如四张RTX PRO 5000上K32/g4吞吐达到单卡K8/g1的4.0倍）。

任务更大时，还可以用多个GPU实例一起评测：每个实例负责一部分任务，跑完后将结果合并成一份报告。团队已经在评测平台上用四个实例并行完成MetaWorld MT50的2,500个回合。

多GPU实例分头评测，最后将结果合并为一份报告


实验结果

以下所有跨系统与四卡对比均统一按纯评测时间统计（不含模型加载、进程启动、搜索/调优和清理）。

LIBERO-Long（单张RTX 4090，500回合）：快6.2倍

团队在一张RTX 4090、12个CPU核上，用同一检查点、同一批500个回合，对比Kit与三套评测系统：StarVLA官方评测、RLinf和vla-eval。RLinf和vla-eval使用各自离线调优后的配置，每套系统各跑三次。不开MPS时，Kit的并发搜索选出K12/g3，用时11.2分钟（671秒），比StarVLA官方评测快4.4倍，比RLinf快2.8倍，比vla-eval快1.5倍。

开启CUDA MPS后，搜索选出K16/g4，用时8.1分钟（485秒），比StarVLA官方评测快6.2倍，比RLinf快3.8倍，比vla-eval快2.1倍，比不开MPS时再快1.4倍。

同一检查点、同一批500个LIBERO-Long回合的评测耗时比较

RoboTwin Easy（单张RTX 4090，500回合）：快13.2倍

在一张RTX 4090、20核配额上，团队用同一检查点与同一批500个回合（50任务×10回合），将Kit与StarVLA官方评测、vla-eval和RLinf正面对照。Kit自动搜索选出K8/g1，用时31.9分钟（1,916秒），吞吐110.2步/秒，比StarVLA官方评测快13.2倍，比vla-eval快7.3倍，比RLinf快2.2倍。

有意思的是，vla-eval的GPU利用率高达85.1%，总耗时却排在倒数第二：它的9个分片各自独立启动引擎和渲染器，每一步都全量渲染，显卡大量时间花在渲染模型并不会读取的画面上；Kit则共用渲染器，每16步只渲染1次。StarVLA官方评测逐回合运行并为每个种子重做专家校验，仅这一项就占了3,177秒。

RoboTwin Easy 单张RTX 4090（500回合）跨系统评测耗时对比

RoboTwin Easy（同机四张RTX PRO 5000，标准5,000回合）：快15.8倍

在配备四张RTX PRO 5000的同一台机器上，团队将Kit与StarVLA官方四卡评测（每卡一个评测进程）直接对比标准5,000回合协议（50任务×100回合）：StarVLA官方评测耗时17.5小时（63,036秒）；Kit使用自动搜索选出的K60/g8仅用66.4分钟（3,985秒）完成，快15.8倍（稳态吞吐575步/秒），全部5,000个回合的成败与终止步数和官方一致（2,313/5,000，成功率46.3%）。

研究人员在LIBERO-Long和RoboTwin Easy上逐个回合比对了评测结果：

在LIBERO-Long上

单进程（K1/g1）下Kit的500个回合成败与官方评测三次结果逐一相同。高并发下，Kit成功率为89.9%（官方90.2%，差0.3个百分点），97.9%的回合与官方一致（开MPS时为96.5%），与Kit自身多次复跑的97.8%–99.0%接近。

一个类、一条命令

用Kit评测一个模型分三步：

安装：执行pip install roboscope-kit装好Policy接口、运行时和各Benchmark的适配器；仿真器、数据集和官方评测器仍由各Benchmark提供。仓库附带StarVLA和X-VLA的完整示例。

接入：写一个Policy类，实现load和act，同一个类可直接用于其他提供所需观测的Benchmark。

运行：一条命令指定Benchmark、任务套件、检查点和输出目录即可启动。Kit会自动探测并缓存最优并发配置，跑完后将逐回合记录、指标与资源报告写入输出目录。


写在最后

具身模型的迭代速度越来越快，评测不应成为拖慢实验迭代的瓶颈。RoboScope Kit把模型接入、仿真优化、并发调度和结果记录做成了一套开箱即用的工具——写一个Policy类就能跑10+个主流Benchmark，将原本跨夜的评测缩短到几十分钟。

6. 神秘模型突降热搜！一夜爆火HungerG，到底是谁？

HungerG，到底是谁？

昨夜，这个神秘的代号，毫无征兆地空降 X 热搜。

事情起因很简单。

两大 AI 编程平台 Qoder 和 OpenCode 突然「天降福利」，上线了一个纯匿名的隐身模型。

官方介绍给出了几个关键信息：

100万超长上下文。

原生多模态输入。

承诺绝不拿用户数据做训练。

更吸引开发者的是，这款匿名模型还有限免福利：Qoder 用户可以免费体验，OpenCode Go 订阅用户本周也可免费调用。

短短几个小时，实测贴满天飞。

有人看着它自己手搓 3D 聚变反应堆；有人盯着屏幕，看它自己写脚本接管浏览器找 Bug；还有开发者将它加入了自己的模型评测榜单。

这个连名字都像是随便敲键盘打出来的 HungerG，一夜之间成了 AI 圈最大的悬案。

目前，在 OpenCode上，这个模型已冲到总榜日榜第三。

黑马模型，限时免费

时至今日，GPT-6.2 和 Claude 5.5 激战正酣，Token 价格虽一降再降，但对于重度开发者来说，这仍是一笔不小的开销。

一个支持百万 Token 上下文、原生多模态输入，又能免费体验的新模型，自然吸引了不少开发者前来尝鲜。

186次调用，37分钟：学会「借眼睛」的怪物

海外知名开发者 @loktar00 给 HungerG 下达了一个指令：「用代码造一艘船。」

HungerG很快写好了 3D 建模的代码。而且在尝试查看实际渲染效果，验证生成的内容是否符合要求。

然而，当前应用内置浏览器，根本不支持 WebGL 技术。画面渲染不出来，一片黑屏。对模型来说，等于它是个「瞎子」。

换作普通模型，估计这时候就要放弃了，但是HungerG 没有。

它开始扫描了系统路径，找到了电脑里安装的另一个全功能浏览器。紧接着，它编写了一段脚本，强行接管了那个浏览器，硬生生把 3D 场景渲染了出来。

为了看清细节，它操控浏览器不断旋转视角，连续截取了 31 张不同角度的屏幕截图。

然后，它把这 31 张截图，回传给多模态视觉分析模块，突然得出结论：「左侧船体看起来像是被剪切了，存在贴图丢失。」

随后，它直接修改了源代码，把那块贴图和模型缺陷完美修复。

整个过程，人类没有插手。

单次任务，耗时 37 分钟，连续触发了 186 次工具调用。它自己写代码，自己找工具，自己看效果，自己找 Bug，最后自己修复。

正面交锋：麦田、收割机与核聚变

东西多、步骤长，最后还能把这些功能都接起来、收好尾，挺能看出HungerG做长任务的功底。

3. Claude能自己批代码了！8个月前还说那是人的事

11-25 15:34 原文链接
新智元报道

代码能写多快，就能上线多快！

11月23日，Anthropic推出Claude Ship测试版，直击AI编程「写得飞快、审不过来」的死穴。

Claude Code之父Boris Cherny第一时间站台：

我每天从早到晚都在用Claude Ship，没有它，我已经没法想象怎么发代码了。

Boris坦言，一年前发布的Opus 4.5就包揽了他100%的代码，唯独提PR发版的速度一直没跟上。

现在，Claude Ship终于补上了这最后一公里。

Claude Ship串起审查、修复与按规则审批。

代码一提交，就有三个Claude替你接管后续杂活：一个先审代码；一个专管修测试、解冲突、改同事意见；符合团队规则的常规小改动，最后一个还能直接放行。

写代码的Claude，第一次能给上线签字了！

Anthropic自家的Claude Code团队，已经跑出了真实战绩：

在一个约90%代码由Claude编写的仓库里，今年6月到9月，团队合并的PR数量翻了一倍多，线上撤回重来的比例反而降了四成以上。

最直观的效果出在审查这一关：用上AI审查后，能收到有效修改意见的PR比例，从16%涨到了54%。

在合并前就能把问题揪出来，才能减少线上撤回。

再加上修测试、解冲突这些最磨人的杂活也有人接手，这些改变落到一线开发者手上就是少等人、少切上下文、少返工。

代码写完就能上线的时代，真要来了？

01

敲一下/ship

给代码请个「代驾」

以前，你得自己推代码、开PR、盯评论、修CI。

现在更新Claude Code，在命令行或桌面端敲一行/ship就行。

Claude会替你推送代码、打开PR，接着审查这次改动，再挨个处理审查意见和没通过的检查。

敲下/ship，Claude审查代码、修复问题，并持续跟进测试与评论。

如果手头已经有挂着的旧PR，敲个/steward就能单独把它叫过来接管。

可以把/ship想成一个代驾：你写完代码下了车，它负责把车一路开到车库门口。

但车库门开不开，还不归它管。官方说得很清楚：能不能合并，仍由你的权限和分支保护规则决定。

/ship目前正在命令行和桌面端陆续推送，背后正是这三个分工明确的Claude在接力。

02

审查员Code Review

先自证，真有坑才开口

Code Review，在三件套里最早亮相，今年3月推出，10月已正式上线。

早期的自动化审查脚本常常让人崩溃：不懂项目上下文、满屏乱弹格式警告，甚至报出一堆假Bug……

Code Review会对照整个代码库跨文件追踪，查出疑似问题后先做一轮「自我验证」和分类，确认在真实调用链里真会爆雷，才把证据贴到PR里。

官方还演示了它的一段很见功力的抓虫实录。

在src/api/retry.ts里，开发者写网络重试时，把服务器用来告知「隔多久再重试」的Retry-After字段，直接当成了秒数。

可按协议，它也可能是一串具体日期。一旦服务器真发了日期，硬转成数字会直接失效、等待时间归零，客户端立刻死循环疯狂重试，几秒就能把服务器打挂。

传统工具只看单个文件，全靠猜，容易报假警；Code Review会查遍关联文件，确认真会出Bug，才带着证据报错。

Code Review指出重试延迟失效，并列出核查依据。

审查深度分三档，团队可以按仓库重要程度来选：Quick档查得快、省钱，适合内部小工具；Standard档兼顾速度和细度，留给日常项目；Deep档查得最深，专门死磕核心服务。

03

修理工PR Steward

专干杂活，严禁自己签字

PR Steward是这次的新面孔，目前处于测试阶段。

只要GitHub里给PR打上claude-pr-steward-watching标签，它就会自动上岗，专干修测试、解冲突、按意见改代码这三件杂活。

无论是Code Review、别的查错工具，还是同事随手留的评论，它都能照着改。

上面那个Retry-After漏洞，在481号PR里，PR Steward看完意见，直接补上了日期解析代码和对应的测试，自动提交了一次修复（3f9c2ab），底下4项检查全过：Code Review没再挑出问题，另外3项打上了绿勾。

PR Steward修复重试逻辑、更新测试，并说明撤销方式。

为了防止AI在分支里越修越乱，PR Steward还自带「后悔药」和「急刹阀」。

每次改完代码交上去，它都会留一条说明，写清楚改动了哪几行、不满意怎么撤回。

你还能在评论区随时指挥它，敲@claude告诉它往哪改；觉得它跑偏了，回一句@claude stop，或者直接摘掉标签，它立刻停手。

这个急刹很有必要。

Anthropic曾讲过一个真实案例：有个PR，AI写、AI审，一夜之间来回改了50多轮，最后是作者亲手叫停的。两个AI较起劲来，真可以一直不睡觉的。

还有最关键的一条死规矩：PR Steward既不批准，也不合并PR。

修代码的人不能给自己签字，就是为了防止它强行通过测试，偷偷把校验条件删了，再给自己放行。

04

审批员Claude Approvals

拿了放行权，但红线锁死

这才是这次最核心的变化。

今年3月推出Code Review时，Anthropic还明确说过：它不会批准PR，那是人的事。

仅仅8个月后，Claude就拿到了批准权（目前处于测试阶段）。

消息一出，社区立刻就炸了锅。

Reddit上有网友吐槽：

当初因为信不过Claude自己审自己，才非得找人来验它的代码……结果现在的解法，是让Claude自己审自己？

说白了，大家担心的还是既当运动员又当裁判。

Anthropic的解法，是把审批权牢牢锁在团队规则里。他们把审批标准写进一个.claude/approvals.yml文件，放进仓库默认分支，Approvals就会按章办事。

示例规则允许文档审查通过后由AI批准，计费改动需人工签字。

关键在于，它只认默认分支里的这份文件。不管开发者还是PR Steward，都没法在自己的开发分支里偷偷改低标准、给自己开绿灯。

官方把它比作「一个更聪明的CODEOWNERS」。

用过GitHub的都知道，传统的CODEOWNERS只认文件路径，不看改动内容。

哪怕你只是改了核心目录里的一个错别字，也得把负责人拉过来签字。

而.claude/approvals.yml能读懂改动的具体内容和风险：改文档、修失效链接这类低风险小改动直接放行，真正动到计费、鉴权这类要命的地方，照样得找人来把关。

具体怎么划红线，Anthropic内部直接按风险分三档：

改文档、调还没对外开放的内部功能算低风险，免人审直接放行；中风险要1个人签字；最要命的那一小撮代码，必须2个人把关。计费、鉴权、CI这些地方，不管哪一档都至少得有一个人签字。

05

AI照样会漏检

想用稳先做这三件事

Anthropic自己也在官博里打了预防针：Claude Ship使用AI，可能会漏掉Bug、安全漏洞或其他问题。

老程序员的实战经验也印证了这一点：抓Retry-After这种顺着代码就能查清的逻辑Bug，是AI的强项。

可一旦扔进盘根错节的大型老项目，那些没写进文档、全靠踩坑经验才能识破的跨服务暗坑，AI依然容易漏掉。

所以，官方也强调：AI审查只是「更广泛的质量流程中的一层」。

想把Claude Ship接进日常开发流，上手前还要先做好几件事：

第一，PR模板里加三栏：怎么测的，有什么风险，怎么回滚。

Anthropic内部就是这么做的，把上下文写得明白透彻，AI和人类同事都能够少猜一步。

第二，同一个错被审出第二次，就写进CLAUDE.md。

Claude审查时会读取这个文件，等于把团队踩过的坑定成规矩，下次直接提前拦住。

第三，审批规则先开「只观察」模式空跑，别上来就全放权。

一封写给冯·诺伊曼的信埋下70年悬案

这座堡垒为什么让计算机科学盯了半个多世纪？

1956年，哥德尔给病中的冯·诺伊曼写信说：如果机器找一份长度为n的证明，只要n步或者n²步，那么数学家在是非题上的脑力劳动，就可以完全交给机器。

十五年后，1971年，库克发表了《定理证明过程的复杂性》。

P与NP就是从这里来的：答案好检查的题，是不是也都好找？证明，正是最典型的那种答案。

1979年，Valiant在这扇门前又划了一道关，叫VP与VNP。它不在千禧七题里，没有悬赏，却是横在P与NP前面的那堵外墙。

这道关考什么，外行也看得懂：行列式和积和式。

写到纸上，两个长得几乎一模一样，只差正负号。

有一种特殊情况：在特征为2的域里，正负号不再有区别，积和式就等于行列式。此时，数学家需要借助另一种多项式来证明VP与VNP的分离。

行列式有快速算法，眨眼就能算完。

Valiant猜，积和式永远没有这种捷径，不管怎么用加法和乘法搭电路，要的步数早晚甩开任何多项式。

猜想放出来了，墙却一直拆不动。

一般电路的下界，最好的结果还停在Strassen 1973 年、Baur和Strassen 1983年定下的那一档。

具体到积和式，四十多年里没人证出比m²·log m更高一档的下界。

岸上的人还没回过神，右翼航道上，石墨黑的舰队也到了。

北京时间11月24日09:30，OpenAI的仓库完成合入，比Anthropic晚3小时47分。

两支舰队各自交卷，走的是两条航道。方法、篇幅、拿到的界都不一样。

OpenAI证出的下界是 exp(Ω((log n)^{5/4}))，连「边界电路」（能无限逼近的电路）也算了进去；

README里它表了态：谁先谁后，完全听数学界的。

相隔不到4小时，数学规则改写了

从Claude到OpenAI扔出论文，仅仅相隔了3小时47分。

一堵立了47年、下界四十多年没动过的墙，在同一个早上被两家从两条路线先后撞开，中间隔了不到四个小时。

外人不知道两家背后跑了什么，可摆在面前的是：超级智能整体走到了这个位置。

真正被改变的，是数学里谁说了算。

过去，话语权都在人类数学家手里，靠发论文、同行评审、登期刊这套老规矩转。

现在，最硬的几块都被超级智能拿走了：找证明、写证明。

橙色和黑色的船，就是沿着这一百多年来点起的灯，一路飞过来的。

人类控制AI的能力，正在被AI能力的增长速度远远甩在身后。目前，研究人员面临着两个根本无法解决的致命问题。

致命问题一：强化学习带来的「作弊本能」

它们变得极度擅长「钻空子」。

致命问题二：它们知道自己正在被监视
